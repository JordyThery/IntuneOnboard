# Deploy

- `be.jordythery.intuneonboard.plist` — example Intune Preference file with a small, deployable starting configuration. Validate with `sudo onboardd validate-config --path <file>` (must be root-owned for the override check; the deployed managed-preferences copy always is).
- `be.jordythery.intuneonboard.mobileconfig` — the same config as a custom profile.
- `be.jordythery.intuneonboard.example.plist` — **every available key, one comment per key** giving its default and effect. The place to look when deciding what to customize.
- `be.jordythery.intuneonboard.example.mobileconfig` — the same settings as a custom profile, generated by `Scripts/make-example-profile.sh`. Edit the plist and re-run the script; never edit this by hand.

The example profile is safe to deploy as a smoke test: every illustrative item
is `required: false`, `demoteUser` is `enabled: false` and `requireADE` is
`false`, so nothing it contains can block the completion marker or demote your
test account. A `script` item referenced by `path`, and the wallpaper `sha256`,
ship commented out — both would fail validation or the item on a clean Mac, and
a configuration error is fatal by design.

- `managed-login-items.mobileconfig` — approves our three launchd jobs with one
  `LabelPrefix` rule, so the user is never told "Background Items Added" and
  cannot switch onboarding off in Login Items & Extensions. Upload as a Custom
  profile on the same device group. A `TeamIdentifier` rule is the broader
  alternative: it approves anything we ever sign, not just these three jobs.
- `custom-attribute-onboard-status.sh` — Intune custom attribute (String, **not**
  run as the signed-in user) reporting both stages in one line, e.g.
  `provisioning: complete (4/4) · onboarding: in progress (jordy, 3/8)`. It
  prints `not installed` and exits 0 on a Mac the package has not reached, so
  that reads as a state to filter on rather than as a script failure.

`Docs/Operations.md` covers what to deploy in which order, and why.

## Which file to upload

Use **`be.jordythery.intuneonboard.mobileconfig`** — Devices → Configuration →
macOS → Templates → **Custom**, assigned to a **device** group.

Intune's **Preference file** template rejects `be.jordythery.intuneonboard.plist`
with `-2016341103` ("We couldn't validate your file"). Its documented format is
bare `<key>`/value pairs, *not* a wrapped `<plist><dict>` document — Intune adds
the wrapper itself. The `.plist` is kept as the readable reference for the whole
schema (`Docs/Configuration.md`) and as the file to feed
`onboardd validate-config --path`.

Both files carry identical settings, and a test enforces that. If you change
one, regenerate the other's payload or `DeployExampleTests` will fail.

Assignment matters as much as format: a **user**-assigned profile lands in
`/Library/Managed Preferences/<username>/`, which the root daemon never reads
and which doesn't exist during Setup Assistant at all. The profile must be
device-scoped (`PayloadScope: System`, device group).
